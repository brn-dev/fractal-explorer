# Phone playback benchmark

This standalone APK measures candidate playback costs before adding live curves to the wallpaper player. It has a separate application ID (`org.fractalexplorer.curvebench`), no permissions, no network access, and no access to the wallpaper app's storage. It does not change wallpapers, install an update, or run in the background. It saves its own JSON reports to `Downloads/FractalBench` using Android's scoped Downloads provider, with Share/Copy as a fallback.

Build with `./android/benchmarks/build-curvebench.ps1` from the repository root. The existing Android SDK tools, JDK 21, FFmpeg and development keystore must be available. Output: `artifacts/curvebench/fractal-playback-benchmark-1.0.apk`. Build runs 1,300 checks for statistics, signed/unsupported current readings, counterbalanced order and LUT coordinates, then verifies the signed APK. The ordinary wallpaper APK is not rebuilt or replaced.

Install and open **Fractal playback benchmark**. Pick Current screen, Cover (1080 × 2520), Main (2256 × 2504), or Both target sizes. Choose 15 fps for ordinary steady playback or 30 fps for entries/smoother loops. The default profile is inferred from the current window width; choose the explicit profile if the phone uses a scaled logical resolution. Fold or unfold before a run and leave the app visible.

- **Quick comparison:** roughly a minute per profile. Each path has two seconds of warmup and four seconds of measurement, repeated in reverse order. Measures synchronized GL draw/driver service and GL-thread CPU time at the selected video cadence. This is not a GPU-only timer query and cannot establish battery drain. Direct decoding has no app GL pass to time; use the power test for that comparison.
- **Unplugged power comparison:** roughly six minutes per profile. Five-second warmup and thirty-second measurement blocks, again in reverse order. No `glFinish` synchronization. Samples signed battery current, voltage, charge counter and temperature once per second, and records thermal state. Power numbers are whole-phone estimates. Fixed display brightness, stable room lighting, no charging and idle background apps make results less noisy. Short runs can remain inconclusive even after counterbalancing; battery percentage is too coarse for this purpose.

Both modes run the same five paths: direct MediaPlayer output to the display surface, the current external-texture GL pass with per-frame location lookups, the same pass with cached locations, a brightness LUT pass, and a master-tone-plus-RGB LUT pass. The source video and target size are the same within each profile. The LUT is a linearly sampled 256 × 1 RGBA8 texture (one extra lookup for brightness, four for tone plus RGB). Identity curves preserve the displayed colors, avoiding the OLED power reduction that darkening the image would otherwise introduce. LUT generation/upload happens only during setup, not every frame.

The bundled fixtures are two-second, silent H.264 excerpts of the existing fractal videos, upscaled to each target size at CRF 20. The 15 fps originals are also encoded at 30 fps with duplicated frames to exercise the higher decode/display cadence. They are representative playback loads, not full-detail native fractal renders. Their compression and decoding load are not universal. The benchmark uses a foreground SurfaceView proxy; the live wallpaper's SurfaceFlinger/HWC decisions may differ beneath a launcher or lock screen. A lower-cost direct decoder path also needs separate verification of cropping, first/last-frame handoffs and fold transitions before shipping it. Existing full-screen rendering uses the same ES2 sampling shader as the current player, but the proposed curves are an experiment here, not a shipped wallpaper setting.

Stop, leaving the app, locking the screen, resizing/folding during the run or severe thermal state ends the test and saves completed blocks. Connecting a charger stops a power run. No continuous redraw is scheduled between decoded video frames. Share the JSON report for analysis; compare brightness/full curves with **Cached GPU playback**, and direct/cached playback with **Current GPU playback**. Inspect callback rates, errors, sensor availability, temperature changes and the two individual repeats before drawing conclusions. Emulator numbers are validation only and never stand in for phone measurements.

For local emulator verification only, `adb shell am start -S -n org.fractalexplorer.curvebench/.BenchActivity --ez verify true` runs short 96 × 128 fixtures. Add `--ez power true` to exercise power-mode bookkeeping, `--ez native true --ez both true` for the full target fixtures, or `--ei fps 30` for 30 fps. These overrides are ignored on physical devices. The app is debuggable so the emulator harness can read its private JSON; the tool can be uninstalled independently after collecting phone reports.

Android's [video power guidance](https://developer.android.com/media/media3/exoplayer/battery-consumption) favors direct SurfaceView output over texture-based composition where practical, while emphasizing device-specific performance. [Hardware Composer](https://source.android.com/docs/core/graphics/hwc) may use display overlay planes instead of GPU composition; the OEM makes that decision. [BatteryManager](https://developer.android.com/reference/android/os/BatteryManager) documents current in microamps (negative while discharging). The report retains raw readings and marks unsupported, charging or unexpected-sign data unavailable rather than inventing zero power.

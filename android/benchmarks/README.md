# Phone playback benchmark

This standalone APK measures candidate playback costs before adding live curves to the wallpaper player. It has a separate application ID (`org.fractalexplorer.curvebench`), no permissions, no network access, and no access to the wallpaper app's storage. It does not change wallpapers, install an update, or run in the background. It saves its own JSON reports to `Downloads/FractalBench` using Android's scoped Downloads provider, with Share/Copy as a fallback.

Build with `./android/benchmarks/build-curvebench.ps1` from the repository root. The existing Android SDK tools, JDK 21, FFmpeg, pinned host JSON runtime and development keystore must be available. Output: `artifacts/curvebench/fractal-playback-benchmark-1.1.apk`. Build runs host checks for statistics, unsupported sensors, randomized plans, integration over irregular timestamps, exact randomization/interval coverage, simulated background bursts, sustained effects, sensor lag and invalid controls, then verifies the signed APK. The ordinary wallpaper APK is not rebuilt or replaced. Version 1.1 updates the standalone benchmark, preserving its earlier reports.

Install and open **Fractal playback benchmark**. Pick Current screen, Cover (1080 × 2520), Main (2256 × 2504), or Both target sizes. Choose 15 fps for ordinary steady playback or 30 fps for entries/smoother loops. Pick one power comparison: cached GPU versus full curves (default), cached GPU versus brightness, current versus cached GPU, or current GPU versus direct decoder output. The default profile is inferred from the current window width; choose the explicit profile if the phone uses a scaled logical resolution. Fold or unfold before a run and leave the app visible.

For actual panel power, run Cover while folded and Main while unfolded. Both target sizes tests two framebuffer sizes on the currently active physical panel; it does not fold the phone or measure the other panel's power.

- **Quick comparison:** roughly a minute per profile. Each path has two seconds of warmup and four seconds of measurement, repeated in reverse order. Measures synchronized GL draw/driver service and GL-thread CPU time at the selected video cadence. This is not a GPU-only timer query and cannot establish battery drain. Direct decoding has no app GL pass to time; use the power test for that comparison.
- **Paired power test:** about **25 minutes per profile** (about 50 minutes for Both). One baseline calibration has 15 seconds of settling and 60 seconds of readings. Eight randomized four-block ABBA/BAAB quartets follow, each block having 15 seconds of settling and 30 seconds of measurement. Four quartets use each orientation, shuffled before measurement using a recorded seed. There are 33 stages per profile and no outcome-dependent early stopping, retries or automatic extensions. No `glFinish` or per-frame clock/CPU timing and no per-frame timing-object allocations; GPU callbacks only increment a cadence counter. This avoids adding profiling costs to the GPU paths when comparing against direct output. Samples signed battery current, voltage, charge counter, temperature, thermal state, manual brightness setting, display refresh rate, power-saving state and app CPU time once per second. Power numbers are whole-phone estimates. The test requires fixed manual brightness and no charging; severe heat, changed brightness/power-saving mode, unusable playback or insufficient current readings during calibration stop it rather than spending the remaining battery on an invalid run. It cannot stop other apps or identify which process caused a spike.

Quick comparison runs five paths: direct MediaPlayer output to the display surface, the current external-texture GL pass with per-frame location lookups, the same pass with cached locations, a brightness LUT pass, and a master-tone-plus-RGB LUT pass. Power comparison isolates the selected A/B pair. Curve cost is compared against the same cached GPU path without curves, keeping uniform-lookup optimization separate from curve cost. The source video and target size are the same within each profile. The LUT is a linearly sampled 256 × 1 RGBA8 texture (one extra lookup for brightness, four for tone plus RGB). Identity curves preserve the displayed colors, avoiding the OLED power reduction that darkening the image would otherwise introduce. LUT generation/upload happens only during setup, not every frame. The measurement overlay is identical for A and B; method/progress text is shown during settling.

## Anomaly and uncertainty analysis

All raw measurements, settling traces, planned order and reasons for quality flags are retained. `PowerAnalysis` adds derived tables without changing them:

1. Integrate current × voltage over actual timestamps. Duplicate/conflicting/out-of-order readings are reported. Do not bridge a missing-data gap longer than 2.5 seconds. Blocks require at least 90% valid time coverage. Observed time centroids, rather than idealized equally spaced times, are used for drift adjustment.
2. Split each block into five-second time-weighted windows. Label windows outside the median ± 3.5 × max(20 mW, 1.4826 × MAD). A separate symmetric winsorized estimate limits their influence without removing their raw energy. A flag means a potential transient, not proof of foreign background work. More than 40% flagged time makes the block unsuitable for inference. Genuine repeated workload bursts can make raw and adjusted results disagree; they are never silently treated as free power savings.
3. In each ABBA/BAAB quartet, interpolate the outside blocks at the inside blocks' actual time centroid. This cancels a linear common drift. Also keep the ordinary uncorrected B − A contrast. Non-linear drift and method-induced carryover are not guaranteed to cancel.
4. Use the **eight quartets** as inference units, not hundreds of correlated one-second samples. Enumerate all 70 balanced assignments. Invert the randomization test under a constant additive-effect/fixed-timing model to produce a conservative 95% interval hull. Report raw and spike-limited intervals, p-values, per-quartet effects and a robust quartet median. Intervals describe statistical variation under that model; they do not include unknown fuel-gauge calibration error or prove isolated GPU power.
5. Flag missing/failed blocks, unknown/adaptive/changed brightness, thermal-state changes or moderate throttling, temperature shifts over 3°C within a quartet, frame cadence below 85%, and known decoder drops above 5%. Direct output also requires usable decoder frame-count evidence, since a frozen output must not look like an efficiency win. App CPU time is only this process, not the decoder service or a monitor of other apps. Refresh-rate differences are recorded rather than automatically removed, because a direct playback path can legitimately change display policy. Physical panel brightness is not available through this tool's public SDK; a fixed setting and stable room lighting remain necessary.
6. Check ABBA versus BAAB disagreement and treatment-aligned first-to-last-window trends for residual settling, workload evolution or sensor lag. A direction is resolved only with all eight usable quartets, valid controls, and raw/adjusted intervals that agree and exclude zero. Effect sizes differing by more than max(1 mW, 25%) or materially non-overlapping intervals are anomaly-sensitive. Otherwise report **inconclusive**, never “zero overhead.” Partial/verification runs have no phone-power verdict. No block or quartet is removed merely for consuming more power; invalid data prevents a formal verdict rather than allowing a favorable subset to decide it.

The procedure reduces nuisance influence and exposes sensitivity. It cannot reconstruct an unknowable background process, guarantee that a firmware-filtered gauge settled in 15 seconds, or make small differences measurable on every phone. Larger uncertainty or repeated anomalous runs may require external instrumentation rather than more mathematical adjustment.

The bundled fixtures are two-second, silent H.264 excerpts of the existing fractal videos, upscaled to each target size at CRF 20. The 15 fps originals are also encoded at 30 fps with duplicated frames to exercise the higher decode/display cadence. They are representative playback loads, not full-detail native fractal renders. Their compression and decoding load are not universal. The benchmark uses a foreground SurfaceView proxy; the live wallpaper's SurfaceFlinger/HWC decisions may differ beneath a launcher or lock screen. A lower-cost direct decoder path also needs separate verification of cropping, first/last-frame handoffs and fold transitions before shipping it. Existing full-screen rendering uses the same ES2 sampling shader as the current player, but the proposed curves are an experiment here, not a shipped wallpaper setting.

Stop, leaving the app, locking the screen, resizing/folding during the run or severe thermal state ends the test and saves completed blocks. No continuous redraw is scheduled between decoded video frames. **Share report** attaches an immutable JSON file using a read-only, explicitly granted content URI; multi-megabyte traces do not go into Android's size-limited message text. **Copy summary** copies the short result only. Reports also save to `Downloads/FractalBench`, with a private copy when that provider is unavailable. Inspect raw and sensitivity estimates, quality flags, uncertainty, cadence, sensor availability and temperature before drawing conclusions. Emulator numbers validate the tool and never stand in for phone power measurements.

For local emulator verification only, force-stop the benchmark package and launch `adb shell am start -n org.fractalexplorer.curvebench/.BenchActivity --ez verify true` for short 96 × 128 fixtures. Add `--ez power true` for all 33 paired stages, `--ei comparison 0…3` and `--el seed 83` for replay, `--ez native true --ez both true` for full target fixtures, or `--ei fps 30` for 30 fps. These timing/seed overrides are ignored on physical devices. `build-device-tests.ps1` builds a separate emulator-only instrumentation APK: it checks byte-exact streaming of a >3 MiB report, metadata, read-only/path restrictions, restoration and opening the sharing chooser without selecting a recipient. The app is debuggable for the emulator harness; it can be uninstalled independently after collecting phone reports.

For host replay, the build's `tests` directory contains `AnalyzeReport`. Run it with that directory and the pinned `json-20240303.jar` on the Java classpath, passing a report filename. It uses exactly the APK's `PowerAnalysis` implementation. The documented method and thresholds are versioned in every power report.

Android's [video power guidance](https://developer.android.com/media/media3/exoplayer/battery-consumption) favors direct SurfaceView output over texture-based composition where practical, while emphasizing device-specific performance. [Hardware Composer](https://source.android.com/docs/core/graphics/hwc) may use display overlay planes instead of GPU composition; the OEM makes that decision. [BatteryManager](https://developer.android.com/reference/android/os/BatteryManager) documents current in microamps (negative while discharging). [NIST's blocked-design guidance](https://www.itl.nist.gov/div898/handbook/pri/section3/pri332.htm) motivates blocking/randomization, and its [outlier guidance](https://www.itl.nist.gov/div898/handbook/eda/section3/eda35h.htm) distinguishes labeling/accommodation from simply deleting unusual observations. The custom protocol's assumptions and conservative gates above remain part of interpreting its result.
